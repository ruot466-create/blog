### D4｜博客的真实定位（2026-10-11 用户澄清）
**结论**：
- **博客 = 放"成长"的地方**：成长记录 + 游戏日常 + 练琴日常（+ 技术），同时兼作**给别人的个人名片**（"以后拿给别人看，方便他了解我"）
- **Obsidian = 私人知识库/数据库**：复习、学习、刷题、看书、记笔记、放资料

**理由**：用户明确表示 Obsidian 里"几乎没有自己的成长"，它的用途是工具性的；博客承载的是"我是谁、我在做什么、我怎么长大的"。

> ⚠️ **修正**：本文件初版曾推断"写作需求已被 Obsidian 满足，博客可降级为纯技术作品集"——**该推断错误，已作废**。
> 错误原因：把"篇数对比"当成了"需求重叠"，但两者内容类型根本不同（数据库 vs 叙事），不构成替代关系。

### D5｜内容的真相源与备份
**结论**：以 git 仓库为唯一真相源；额外备份到 Obsidian 属可选项，非必要措施。
**理由**：博客 Markdown 在本地 `blog/` 与 GitHub 各存一份，且部署走 GitHub Pages（`.github/workflows/deploy.yml`），不依赖第三方平台存续。真正会"让博客消失"的是**账号或域名层面的问题**，不是内容丢失。担心的对象应该是"账号安全"，不是"文件备份"。


### D6｜记录粒度：阶段总结为主 + 专题穿插（Q8 答案）
**结论**：**不写流水账**。以「阶段总结」（一段时间做了什么、想通了什么）为主，不定期穿插「专题」（一个项目 / 一段经历完整讲清）。
**理由**：用户明确选择 B+C 结合。

### D7｜内容分板块（Q9 答案）
**结论**：不同类型的内容**分开**，不混在一条时间线里。
**技术事实（已查证）**：Fuwari 的分类由文章 frontmatter 的 `category` 字段决定，**单值**——一篇文章只能属于一个分类。**不需要改任何配置文件**，新建文章时写不同的 `category` 即可。
**待定**：具体分几个分类（见 P5）。


### D8｜分类方案：A（3 类）—— Q9 落定
**结论**：分成 **成长 / 技术 / 生活** 三类。
- **成长**：阶段总结（本周/本月做了什么、想通了什么）
- **技术**：专题（项目、踩坑、学到的东西）
- **生活**：游戏日常、练琴、杂事

**理由**：当前只有 1 篇文章，分 4 类会有 3 类是空的；点进去显示「暂无文章」比没有这个分类更糟。练琴等细分先用 `tags`（多值）承担，攒够量再拆。
**相关**：`hello.md` 的 category 由「随笔」改为「成长」。
